3. PLAYER LIFECYCLE IS THE CENTRAL REQUIREMENT
Streams must not be paused, reloaded or recreated by our application merely because I reorder tiles, resize the viewport, toggle a sidebar, switch chat, select a stream or change the layout.

Give each channel a persistent player instance and mount location. Separate visual placement from player lifetime. Stable React keys alone are insufficient: moving/reparenting an iframe can reload its browsing context. Prefer a stable player surface whose tile positions/sizes change through layout styles. Inspect the actual DOM and instrument creation, removal and frame navigation.

When profiles overlap, preserve player instances for retained channels. Explicit reload, removal and genuine channel replacement are legitimate lifecycle changes. Ensure development-mode effects do not leave duplicate players or listeners.

Represent playback intent separately from observed state. Manual pause must remain paused; recovery must not repeatedly override it. Distinguish buffering, offline, playback blocked and errors. Avoid blind reload loops and periodic force-play hacks.

Use Twitch's supported player integration. Check its current API, sizing, embedding and autoplay requirements. Resolve quality choices from each player's available qualities, with an explicit fallback when the requested quality is unavailable. Show the actual quality separately from the preference. Default new streams to muted and offer a clear user-gesture start/unmute path where needed.

Browser suspension, Twitch policy and network failures cannot be eliminated by an app guarantee. Verify what happens when focus/tab visibility changes and report external limits separately from application-caused interruptions. Do not claim uninterrupted playback beyond what was tested.

4. RECREATE THE CORE WATCHING EXPERIENCE
Build real channel input with normalization, validation and duplicate handling; stream search; accessible reorder controls; removal and clear-all; persistent ordered lists; the sidebar; and usable empty/error states.

Reproduce observed layout rules. Where evidence is incomplete, use a documented deterministic fallback that fits useful video area, preserves video proportions, and handles incomplete rows without cropping. Respect current minimum embed sizes: use a reasonable scrolling layout when every stream cannot fit. Keep focus/enlargement and sidebar/chat resizing independent of player lifetime.

Provide independent audio controls, available quality selection, global quality preference, and the observed global play-paused, pause, mute and reload controls. Define and display how global settings interact with per-stream overrides. Never silently unmute all streams because one tile or chat channel is selected.

Implement profiles and session restoration with a versioned schema in namespaced localStorage; use IndexedDB only if the actual data warrants it. Include schema migrations, safe recovery from malformed data, and clear handling of blocked storage or quota errors. Do not silently erase existing data. Save profiles, stream order, preferences, quality/audio choices and chat-panel settings locally; do not persist live player objects or claim playback can resume without browser permission. Provide a JSON backup download and validated restore, with explicit merge/replace behaviour. Explain that storage is specific to this browser and site origin: private browsing, clearing site data, another device, or a different preview/custom domain can mean different or missing data. Backups allow transfer between them. Import must validate structure, channel values and size limits before changing state. Share only the intended public watch configuration, never tokens or private settings. Use self-contained share codes or URL fragments, never server-stored profiles or a URL-shortening backend. Validate shared input before applying it and avoid silently overwriting saved profiles. Limit URL payload size and offer a file export when too large. No telemetry or remote upload of local profile data. Investigate compatibility with existing Viewington profile codes; implement it if feasible and verified, otherwise clearly document the format difference.

Implement online/offline/unknown/error states. Reproduce offline hiding and restoration without disturbing other players or their order. A failed status request is not evidence that a channel went offline. Hidden/removed offline players still need a mechanism to discover that the channel returned.

Use a replaceable, browser-only status provider based on supported Twitch player events. Investigate whether those events reliably detect return-to-live while an offline tile is hidden. Do not destroy the only status observer and then expect notifications. Use bounded, documented recovery where feasible without interrupting other players. If a channel cannot be observed reliably, show unknown/stale status and a refresh action; record the parity limitation. Do not add a backend to solve it. Do not rely on Viewington's private backend, an unofficial CORS proxy, a developer's personal token, or a client secret in the frontend. Core playback, profiles and chat must work without an app API key. If richer metadata would require a future browser OAuth integration, document that as an optional future extension rather than expanding this build.

5. INCLUDE ONE SWITCHABLE CHAT PANEL
Add one right-hand panel, with collapse and resize controls, a channel selector, and an explicit "Open chat" control for each stream outside its iframe.

Use the official Twitch chat embed for the initial implementation. Show which channel is selected, handle no-channel/removed-channel states, and persist the selection and panel width. Switching chat must affect only chat. Keep audio selection independent unless I explicitly enable a follow-audio option later.

Use current Twitch embedding configuration for local development and deployed hostnames. Support the embed's normal signed-in interaction where available; clearly handle login/storage restrictions and provide an "Open chat on Twitch" fallback. Do not pretend to read messages from or manipulate the cross-origin chat DOM. Leave a small typed ChatProvider boundary for a future custom chat client.

6. DESIGN FOR EXTENSION WITHOUT OVERBUILDING
Separate:

- Player adapter and instance lifecycle management.
- Layout calculation and presentation.
- Browser-only live-status provider and explicit capability/limitation reporting.
- Chat provider and panel UI.
- Typed commands for controls and keyboard shortcuts.

Use narrow interfaces and normal modules, not a speculative plugin platform. Keep transient player objects outside serialized state. Use capabilities for integrations whose features differ. Make adding a future panel, control or provider straightforward without editing the player lifecycle.

Document the player lifetime invariant, state ownership, dependency boundaries, profile schema, configuration and the steps to add another panel/provider. Keep keyboard shortcuts out of text fields and avoid overlays that obstruct normal Twitch player interaction.
